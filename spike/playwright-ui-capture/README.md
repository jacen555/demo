# spike/playwright-ui-capture

## The question

> **Can Playwright drive a real web UI while capturing deterministic, frame-accurate
> output suitable for the existing SizzleCraft video pipeline — including a visible
> synthetic cursor, per-segment speed control, and zoom?**

Falsifiable form, in the terms the pipeline actually cares about:

1. **Determinism** — does the same interaction script, captured twice, produce a
   frame sequence whose per-frame SHA-256 hashes are **identical**, on a page that
   contains `Date`-, `setTimeout`-, `requestAnimationFrame`- and CSS-animation-driven
   content? Specifically: **does `page.clock` stay pinned while Playwright *actions*
   are running**, or do actions internally wait on real time and let wall-clock leak
   into the pixels?
2. **The cursor** — Playwright screenshots exclude the OS cursor. Can the coordinates
   an action targets be known ahead of the action, and can an injected overlay be
   drawn there and appear in the screenshot, **without** stealing hit-testing?
3. **Speed control** — can N frames be emitted per action (hold on a click, skim a
   long form fill), and what is the cleanest model?
4. **Zoom** — CSS transform on the page vs. crop-and-scale at capture time: which
   gives better text quality, and which animates smoothly?
5. **Integration cost** — how much of `frame-capture.mjs` survives, and is this a new
   mode inside it or a sibling script feeding the same downstream stages?

### The design fork being resolved

| | Mechanism | Hypothesis |
|---|---|---|
| **Option A** | Playwright `recordVideo` — film the page while driving it | Simple, but discards variable frame timing, frame-level control, dedup, and the timing solve |
| **Option B** | Scripted interaction + per-frame screenshot capture, with `page.clock` pinning time | Preserves determinism, frame hashing, the timing solve, and the cheap audio-only remux path |

The commissioning expectation was that **B wins**. This spike tries to falsify that —
if `recordVideo` is good enough it is a far smaller change.

## How to run

```powershell
cd spike/playwright-ui-capture
npm install            # playwright only; browsers already in the ms-playwright cache
npm run experiments    # runs E1-E5, writes results/*.json and a summary table
```

Individual experiments:

```powershell
node src/e1-record-video.mjs     # Option A: what recordVideo actually guarantees
node src/e2-determinism.mjs      # Option B: 3 arms x N runs, logical + raster hashes
node src/e3-cursor.mjs           # synthetic cursor + pointer-events hit-testing proof
node src/e4-speed.mjs            # per-step frame budgets from one timeline
node src/e5-zoom.mjs             # CSS transform vs crop-and-scale, measured sharpness
```

Supporting probes (not part of the headline result, but they produced numbers quoted
below):

```powershell
node src/probe-raster-flags.mjs  # are the Chromium raster flags load-bearing?
node src/probe-capture-cost.mjs  # ms/frame at 720p / 1080p / 4K
node src/diagnose-divergence.mjs # dump + diff any frames that differ between two runs
```

Everything targets `target/app.html`, a self-contained local page committed in this
spike. No network, no live site, no credentials anywhere.

## Layout

| Path | What |
|---|---|
| `target/app.html` | The driven UI. Deliberately hostile to determinism: live `Date` clock, `setTimeout` state machine, `requestAnimationFrame` progress bar, CSS keyframe spinner, plus small text for the zoom test |
| `src/timeline.mjs` | The step/frame-budget model — ms authored, frame-indexed plan executed |
| `src/cursor.mjs` | Synthetic cursor overlay: injection, move, progress-driven click affordance |
| `src/driver.mjs` | The driven-capture loop — clock pinning, animation freeze, action dispatch, signature, screenshot |
| `src/e1..e5-*.mjs` | One experiment per question, each writing `results/<name>.json` |
| `src/probe-*.mjs` | Supporting measurements (raster flags, capture cost) |
| `src/diagnose-divergence.mjs` | Diagnostic: locate and visualise what differs between two runs |
| `src/lib/*.mjs` | Frame hashing, PNG pixel analysis, bundled-ffmpeg shell-out |
| `results/` | Measured output — regenerated by `npm run experiments` |

## Answer

**Yes — via Option B. Playwright can drive a real web UI and produce byte-identical,
frame-accurate PNG sequences that drop straight into the existing pipeline. Option A
(`recordVideo`) cannot, and the reason is structural, not a tuning problem.**

Measured on this machine (16 cores, Playwright 1.62.1, Chromium 151.0.7922.34,
1280×720 @ 30fps unless stated). Regenerate with `npm run experiments`.

### Option A is disqualified — `recordVideo` (E1)

Two runs of an identical scripted interaction produced **different artifacts**:

| | run 1 | run 2 |
|---|---|---|
| file size | 149,565 B | 78,164 B |
| coded frames | 58 | 57 |
| decoded frames identical | \_ | **no** |

The source explains why (`playwright-core/src/server/videoRecorder.ts`, bundled in
`lib/coreBundle.js`):

- `var fps = 25` is a **module-level constant**. `recordVideo` exposes no fps option, so
  the pipeline's 30fps cannot be honoured.
- Frame timestamps come from `frame.frameSwapWallTime` — **compositor wall-clock**.
  `page.clock` virtualises time *inside the page*; it never reaches the recorder.
- `frameNumber = Math.floor((timestamp - firstFrameTimestamp) * fps)` buckets frames by
  real arrival time. Two frames landing in one 40 ms bucket means the earlier one is
  **discarded**; a quiet page emits nothing at all.
- `_stop()` pads the tail from `monotonicTime()` with `Math.max(addTime, 1)` — **at
  least one second of wall-clock-dependent tail**, always.
- The encode is fixed at `-c:v vp8 -b:v 1M -crf 8 -deadline realtime -speed 8`: lossy,
  speed-optimised, ~1 Mbps. At 4K that is not a usable master.

This is not a knob that can be turned. `recordVideo` is a debugging aid.

### Option B works, and three controls are each load-bearing (E2)

Same script, three arms, 225 frames, runs compared frame-by-frame. **Logical**
determinism (page state) and **raster** determinism (PNG bytes) measured separately:

| arm | clock | anim freeze | logical identical | raster identical | ms/frame |
|---|---|---|---|---|---|
| naive | ✗ | ✗ | **0 / 225** | 0 / 225 | 79.3 |
| clockOnly | ✓ | ✗ | **225 / 225** | 161 / 225 | 35.1 |
| full | ✓ | ✓ | **225 / 225** | **225 / 225** (3 runs) | 35.1 |

- **`page.clock` survives Playwright actions.** This was the crux risk, and the answer is
  yes — by design, not luck: Playwright's actionability polling runs on
  `injected.utils.builtins.requestAnimationFrame` / `builtins.setTimeout`, references
  snapshotted at injection time and deliberately immune to page-level overrides. So the
  driver waits on real time while the page sees only virtual time.
- **CSS animations need a separate freeze.** `page.clock` does not control the
  compositor's document timeline. The unfrozen spinner alone broke 64 of 225 frames
  (worst pixel delta 186/255). The fix is the pause + negative-`animation-delay`
  technique `frame-capture.mjs` already uses — but it must re-scan every frame, because a
  driven DOM grows new animated elements mid-script.
- **Chromium raster flags are required for bit-exactness.** Without
  `--disable-partial-raster` (+ checker-imaging, srgb), 73 of 225 frames diverged across
  3 runs. Chromium re-rasterises only the invalidated part of a tile, so a pixel's value
  depends on what was drawn there before. With the flags: 0 divergent.

Wall-clock spread across 3 runs: **69 ms on 7.9 s (0.9%)**. Dedup opportunity on the demo
script: **29 / 225 consecutive duplicate frames (13%)**.

### The cursor (E3)

- **Coordinates are predictable.** `locator.boundingBox()` centre vs the `clientX/clientY`
  the page actually received: worst error **0.14 px** across three targets.
- **The overlay appears in the capture** — 882 pixels drawn, max channel delta 239.
- **`pointer-events: none` is mandatory, and that is proven, not assumed.** With
  `auto` the overlay intercepts the click: `page.click` times out and the app's handler
  runs **0** times. With `none`: handler runs **1** time.
- **The click affordance must be progress-driven, not CSS-animated** — under a paused
  clock a CSS ripple simply freezes. Driving radius/opacity from the step's 0→1 progress
  is frame-exact and deterministic by construction.

### Speed control (E4)

Author in **milliseconds per step**; derive frames. Same unit as the audio timing solve,
so a step duration can come straight from a narration segment, and render fps stays a
render knob rather than a script rewrite.

One real defect found and fixed: **rounding each step's duration independently
accumulates drift** — +140 ms (3.5 frames) at 25fps on a 15-step, 7500 ms script. Rounding
*cumulative boundaries* instead bounds total error to under one frame at any fps:

| fps | frames | duration | drift | naive-rounding drift |
|---|---|---|---|---|
| 24 | 180 | 7500 ms | 0 ms | +42 ms |
| 25 | 188 | 7520 ms | +20 ms | **+140 ms** |
| 30 | 225 | 7500 ms | 0 ms | 0 ms |
| 60 | 450 | 7500 ms | 0 ms | 0 ms |

140 ms is enough to visibly desync a demo from its voiceover.

### Zoom (E5)

Both mechanisms compared against a **ground truth** — the same region rendered at
`deviceScaleFactor = 2.5`, a genuine supersample — rather than against each other:

| | RMSE vs ground truth | acutance (mean gradient) |
|---|---|---|
| ground truth | — | 2.661 |
| **CSS transform** | **5.89** | **2.661** (exact match) |
| crop-and-scale | 7.81 | 2.059 (**−22.6%**) |

**CSS transform wins decisively.** It is a true re-render: text is re-shaped at the
zoomed size, and its acutance matches the supersampled reference exactly. Crop-and-scale
has a **6.25× pixel deficit** (= Z²) — 147,456 source pixels stretched to 921,600 — which
no resampling filter can recover. The difference is plainly visible in
`results/zoom/*.png`.

Two practical findings:
- **CSS zoom preserves hit-testing.** Bounding boxes scale correctly (observed scale
  exactly 2.500) and clicks land, so the UI can still be driven while zoomed.
- **Zoom can hide targets.** An element the zoom pushes off-viewport becomes genuinely
  unclickable (Playwright correctly times out). Zoom and interaction targets must be
  planned together — a real authoring constraint.
- Ramping is smooth and deterministic: 12 eased steps, 12 distinct frames, identical
  across runs.

### Integration cost

The downstream contract is just `frames/frame_NNNNN.png`, numerically ordered at constant
fps — exactly what `encode-mp4.mjs` already globs. **A driven capture feeds S7/S8/S9
unchanged.**

The one genuine architectural incompatibility: `frame-capture.mjs` parallelises across
workers *because every frame is a pure function of frame number*
(`masterTimeline.seek(t)`). **A driven UI is a stateful sequence** — frame N depends on
frames 0..N-1 — so that slicing cannot apply, and neither can mid-segment resume.

Measured per-frame cost (3 repeats each, driven, single page):

| resolution | ms/frame | spread |
|---|---|---|
| 1280×720 | 35.8 | 3.4 |
| 1920×1080 | 54.7 | 1.6 |
| 3840×2160 | **158** | 1.6 |

At 4K that is **4.7 s of capture per second of video, single-threaded**, against the 6
workers `frame-capture.mjs` would use for generated content at the same resolution.

**Recommendation: a sibling capture script, not a new mode inside `frame-capture.mjs`.**
The two execution models (parallel pure-seek vs sequential stateful) would fork its core
loop entirely. Extract the shared primitives — capture lock, resume fingerprint, atomic
frame write, `linkOrCopy` dedup, progress/ETA, frame naming, the CSS-animation freeze —
into a module both consume, then let generated segments parallelise and driven segments
run sequentially into the same `frames/` directory.

### Confidence and caveats

- Measured on **one machine, one OS (Windows), one Chromium build**. Bit-exactness across
  machines/OSes is **not** established and should not be assumed.
- The target is a **local, self-contained page**. A real app with network I/O needs those
  responses stubbed (`page.route`) to stay deterministic — not tested here.
- Determinism was measured over **3 runs in one process generation**, not across reboots
  or driver updates.

## Disposition

**Graduate**, into `tools/SizzleCraft` (`sizzlecraft` domain, **Tier 2**) as a sibling
capture path plus a shared-primitives extraction.

Per constitution §XI the spike is **not** promoted by moving this folder — the real
implementation is rewritten under the gates this skipped (pre-edit approval, tests for
logic-bearing code, independent review). The load-bearing logic that must carry tests:
the timeline compiler's cumulative-boundary rounding, the frame-budget mapping, and the
zoom focal-region maths.

Retain this folder until that task lands — it is the executable reference for the three
determinism controls, which are easy to drop silently and impossible to notice by eye.
