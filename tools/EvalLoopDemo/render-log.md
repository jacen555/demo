### `code` visual mode — segment 2, built this round

The review asked twice for the **actual scenario object** on screen instead of the card
grid, with fields highlighted as they are narrated, explicitly accepting that it reads
noisier because the noise is the message: it shows how much of the conversation is
configurable. There was no code/monospace/JSON rendering in `write-build-html.mjs` — every
`json` hit in that file was parsing, not display — so this was engine work, not a
parameter. It is now a fifth `visual.mode` behind the existing dispatch.

```jsonc
"visual": {
  "mode": "code",
  "json": { /* inline */ },          // or "jsonFile": "…", confined to the project
  "caption": "scenarios.json — phrasings elided; internal ids removed",
  "highlights": [ { "path": "facts[1]", "atMs": 30589 } ]
}
```

Fields are addressable by JSON path, emitted as DOM ids (`scenario-path-facts-1`) the same
way diagram nodes are, and driven by a `codeFocus` trigger on the existing trigger switch.

**Highlight times come from the measured word boundaries in `timing.json`, not estimates.**
That is an accessibility requirement, not polish: narration is the only audio track
(WCAG G226), so a field that changes on screen without being spoken is a state change no
listener can follow. Each of the six highlights fires on the word that names it.

**Three guards, each earned:**

1. **A highlight addressing a path that does not exist fails the build**, naming the paths
   that do exist. Rendering nothing is indistinguishable from a highlight the viewer
   missed — this pipeline has already lost a card to exactly that. It is a hard failure,
   not a warning, because a warning scrolls past in a 25-minute render log.
2. **No-go patterns are enforced where the data reaches a frame.** This is the only mode
   that renders source data rather than authored copy, and authored copy is what gets
   human review. `timing.project.noGoPatterns` is checked against the serialised object
   and refuses the build on a match.
3. **`jsonFile` is confined to the project**, like every other on-screen asset.

**Redactions applied to the on-screen object**, and none of them are cosmetic:
`targetSapId` (internal GUID), `reviewItems` (internal finding ids), `description`
(~50 words of taxonomy prose that would dominate the frame), and `answerPool` — 13 real
phrasings elided to a count, because the constraint is *reference the real support data,
never quote it*, and a count references where a list quotes. The caption says so on
screen rather than letting the field look short.

**Two defects found by rendering it, not by reading it.** Both are recorded because both
are the same shape as failures this project has already paid for:

- **The segment rendered blank.** `.codewrap` carries `.el`, so it is hidden until
  revealed, and `codeFocus` targets a *field* — which cannot reveal its hidden ancestor.
  Every trigger resolved and "succeeded" against an invisible element. It surfaced only
  because four preview frames sampled at four different timestamps came back
  **byte-identical**. That check is now a test.
- **The client-side block is emitted as one line inside a template literal**, so a `//`
  comment swallows the rest of the file and a backtick in a comment is parsed as a nested
  template. Both produced runtime errors far from the edit.

### `validate-timing` contiguity — a check that could never pass

Running the merged verifier against this project failed all 8 segments. The check asserted
strict adjacency (`startMs === previous endMs`), but **`voice.mjs` deliberately inserts
inter-segment silence** — the perceived gap — so every timeline the real pipeline produces
is monotonic but *not* adjacent. Measured here: a uniform 1,416 ms between segments and
1,920 ms of lead-in.

This is the exact mirror of the `ajv.errors` defect on the other side of the same file: one
check could never fail, this one could never pass. The second is worse in day-to-day use,
because it trains the reader to ignore a red line.

Now: **an overlap fails** (that is the thing actually wrong), a gap passes and is reported,
and an **uneven** gap is called out while still passing, since unevenness usually means a
hand-edited window. Contiguity now reads
`OK (8 inter-segment gap(s), UNEVEN: 1416, 1920 ms)` — true, and useful.

### Plan-by-default: what changed at the boundary, and what it cost
The engine audit made every **user-named write** plan by default. Four of the stages this
project drives are affected — `voice`, `write-build-html`, `make-music` and `remux-music`
— and all four now need `--apply`, with `--replace` on top when the output already exists.
`make-music`, `remux-music` and `check-levels` also moved from positional to named
arguments, so the old `remux-music.mjs 1.18 1.50` form is gone.

**This was the right call and it cost this project almost nothing.** The honest report
back to the engine owners:

- **Re-running a stage is now a two-token change, not a one-token one** (`--apply
  --replace`). In a pipeline that is re-run dozens of times against the same output paths,
  `--replace` is typed so reflexively that it is close to being ambient. That is a mild
  erosion of the guarantee rather than a defect, and the alternative — overwriting an
  approved deliverable by default — is plainly worse. Worth knowing, not worth reverting.
- **The plan output turned out to be worth more than the safety.** `write-build-html`
  reporting *"8 segments, 154,757 bytes, output EXISTS"* is a cheap correctness check
  before a 25-minute render, and `remux-music`'s plan now states the loop decision and
  the gain pin. Plan mode became a dry-run diagnostic, which is a genuine gain.
- **One real bug surfaced from the merge.** Duration probing ran before the plan/exit
  branch, so a no-flag run exited non-zero on undecodable media — planning must stay
  answerable about inputs that are stubbed or not yet rendered. Fixed here, with a
  regression test; the plan now prints `loop UNDECIDED` rather than implying no loop is
  needed. This is the class of defect the audit could not have found by reading, because
  it only appears when a stub reaches a stage that assumes real media.

### ⚠️ Correction: TTS is length-deterministic, NOT byte-deterministic

This log previously recorded *"TTS determinism confirmed across 3+ runs."* **That claim was
measured on timings and stated about bytes.** Re-running `voice` on unchanged narration to
record the lineage fingerprint produced:

| | |
|---|---|
| `durationMs`, every segment `endMs` | **identical to the millisecond** |
| every clip's byte **length** | **identical to the byte** |
| every clip's **duration** | identical |
| content hash of 5 of 8 segments + `voiceover.mp3` | **different** |

Same length, same duration, different samples — neural synthesis varies sub-perceptually
between runs while landing on the same frame count. So "deterministic" is true of the
**timeline** and false of the **audio**, and the two were conflated here.

Same error shape as the 74% dedup figure: a real measurement, generalised one step further
than it supported. Byte-identity and timing-identity are different claims, and this project
has now got that wrong in both directions.

**Consequence, and how it was resolved.** The shipped render's audio was encoded from the
pre-re-run clips, so keeping the new ones would have left the deliverable perceptually
correct but no longer reproducible from the inputs on disk. The lineage fingerprint is a
hash of the narration **text**, not of the audio, so the two are separable: the re-run
`calibration-observed.json` and `timing.json` were kept, and **the audio was restored to the
17 files that produced the shipped MP4.** Lineage is proven and the artifact is exactly
reproducible.

> **The general hazard:** a verification-only re-run can invalidate an artifact when the
> stage that records the proof also regenerates the inputs. Worth checking before re-running
> any stage purely to satisfy a checker.

## Defect found by decoding: the perceived gap is ~335 ms long — ACCEPTED

`voice.mjs` solves each gap as `target − tail − head`, taking tail and head from
msedge-tts **word-boundary metadata**. That metadata reported **tail = 0 ms on all eight
clips**, so the solver inserted 1,416 ms expecting a 1,500 ms perceived gap.

`silence-scan.mjs`, which **decodes**, measures the real gaps at **1.80–1.92 s**. The
implied real tail is ~335 ms — matching the **276–312 ms the pipeline contract already
documents**. The contract is right; the metadata is wrong. This is bug-ledger entry 5's
mechanism recurring in a new place, and it is now **entry 13** in that ledger.

### Decision: accept 1.83 s. Do not compensate. This is a continuity decision.

Both sibling projects were checked, and the result changes the reasoning:

| Project | `perceivedGapTargetMs` | `insertedGapsMs` | Decoded? |
|---|---|---|---|
| `interviewer-qna-dataprep` | 1500 | `1416` × 11 (one 1392) | **no `silence-observed.json` — never decoded** |
| `interviewer-qna-delta` | 1500 | `1416` × 8 | **no `silence-observed.json` — never decoded** |
| `eval-loop-demo` | 1500 | `1416` × 7 | yes — **1.83 s measured** |

Same voice, same `rate=+20%`, same backend, same 1,416 ms insert. **Both shipped videos
already carry this defect and already play at ~1.83 s perceived gaps.** Nobody knew,
because nobody decoded.

So accepting is **not** "free and unobtrusive" — that was the wrong framing in the earlier
revision of this file. Accepting is the **continuity-correct** choice: all three videos are
internally consistent at ~1.83 s.

| Option | Verdict |
|---|---|
| **Accept 1.83 s gaps** | ✅ **CHOSEN.** Matches both shipped siblings exactly |
| ~~Set `perceivedGapMs` ≈ 1165~~ | ❌ **DO NOT APPLY. This is a regression against the series**, not a tidy fix. It would make this the only video of the three at 1.5 s — precisely the mismatch `SKILL.md` § *Series continuity* warns is very noticeable on back-to-back playback |
| **Decode tails inside `voice.mjs`** | Deferred. The correct *code* fix, but see below |

**Fixing `voice.mjs` is a series-wide decision, not a silent correctness fix.** The moment
it decodes tails, every future video re-paces to a genuine 1.5 s and no longer matches the
three that exist. That is a deliberate choice about the series, and it belongs to whoever
makes it — not to a passing bug fix. Recorded as bug-ledger entry 13 so the next session
cannot mistake it for housekeeping.

## 4K / 1440p capture probe — measured, not scaled

Run **2026-09-25** on a bounded probe, then **stopped deliberately**: a full 4K capture
would have burned ~2 hours producing frames to discard while the storyboard is still being
edited. `timing.project` was restored to 1920×1080 afterwards.

Machine: **16 cores**. `frame-capture.mjs` uses `cpuCount - 1` workers at ≤1080p but caps
at **6** above it (`heavyFrames = width * height > 1920*1080`) to avoid OOM — so 4K gets
**15 → 6 workers**, 2.5× fewer, on 4× the pixels.

### The result that changes the decision: PNG is the bottleneck, not the pixels

Same protocol for both legs — 75 s warm-up, then a 150 s sample window, dedup off so every
frame is a real screenshot.

| 4K · 6 workers · dedup off | Rate | Bytes/frame | Projected S6 (7,519 frames) | Frame store |
|---|---|---|---|---|
| **PNG** (current default) | **1.00 fps** | 2,183 KB | **~125 min** | **16.0 GB** |
| **JPEG q88** | **13.05 fps** | **170 KB** | **~9.6 min** | **1.25 GB** |

**JPEG is 13× faster and 12.8× smaller at 4K.** Playwright's PNG screenshot is losslessly
compressing 8.3 M pixels per frame, and that — not the worker cap — dominates the cost.

Quality was checked at 1:1 on small type over flat backgrounds (`qc/jpeg-q88-crop.png`):
crisp glyph edges, no ringing, no blocking. Frames verified as `3840x2160` mjpeg.

**So 4K becomes cheaper than the 1080p render we already shipped** (35.4 min at PNG). The
1440p comparison point is therefore not needed to make 4K affordable — it is only relevant
if PNG must be kept for some other reason.

### Was the 6-page cap the binding constraint? Measured — no

Peak RAM across all node + Chrome processes: **2.2–2.3 GB** at 4K, steady, against **64 GB
available**. Nowhere near OOM, so the cap looked over-conservative. **It was measured
rather than assumed, and raising it does not help:**

| Workers | Rate (1,200-frame 4K JPEG run) |
|---|---|
| 6 (the auto cap) | 9.77 fps |
| 10 | 9.87 fps |
| 14 | 9.53 fps |

**Flat.** Something saturates before the core count does — most likely SwiftShader
rasterisation, since there is no GPU and Chrome is compositing in software on the same
cores. ⚠️ **Caveat:** the override was set via `SIZZLECRAFT_WORKERS` and the rate did not
move, but a process-count check was inconclusive (Chromium shares renderers across pages),
so this is *measured, pending confirmation* rather than settled.

**Implication:** making the cap configurable is still reasonable hygiene — a hardcoded 6
is arbitrary — but it is **not a performance lever on this machine**. The frame-format
finding is.

### Dedup at 4K: 0% on the body, and byte-identity is NOT the measure

First attempt measured "74% deduped" by comparing consecutive frame **byte lengths**. That
was wrong, and the way it was wrong is worth recording:

- Length-identical frames *were* byte-identical (MD5 match) — but byte-identity does **not**
  mean the frame was held. A deterministic renderer screenshotting an unchanged scene
  produces identical bytes **at full cost**.
- The real measure is the NTFS **hardlink count**: a held frame is materialised as a link to
  its predecessor. `fsutil hardlink list` shows frame 31 with **58 paths** (genuinely held)
  while frames 1501 and 2711 have **1 each** despite being byte-identical.

Measured properly, across 401 frames sampled from 6 parallel slices spanning the whole video:

| Region | Held |
|---|---|
| Lead-in (frames 0–120) | **57%** |
| Body (280 frames across 5 slices) | **0%** |

**0% on the body**, consistent with the 2% measured over the full 1080p run. The live CSS
background animation trips `__frameSig`'s motion guard, so body frames are never held —
which is why dedup cannot rescue a 4K PNG capture.

> `frame-capture.mjs` splits the timeline into **one contiguous slice per worker, run in
> parallel** — slices began at frames 0, 1497, 2704, 3754, 4886, 6234. A timed probe
> therefore samples the whole video, not just the opening, which makes bounded probes
> genuinely representative.

## 🔴 The music gain was wrong, and the whole-file check is what caught it

**Shipped at `musicGain 1.50` the mix measured −9.8 dB against the sibling's −19.1 —
nearly 10 dB too loud, peak −0.2 dBFS.**

Cause: `1.50` was tuned for the **generated** bed. Measured RMS of each source:

| Source | RMS | Peak |
|---|---|---|
| Generated bed (`make-music.mjs`) | **−43.1 dB** | −25.2 dBFS |
| Licensed track (Pixabay master) | **−11.4 dB** | **+0.6 dBFS** |

**31.7 dB apart.** A commercial master is loudness-normalised and peak-limited; a generated
ambient bed is not. Applying a gain tuned for one to the other put the bed ~32 dB over.

Corrected to **`musicGain 0.055`**, which lands the bed at **−36 dB** — exactly
`knobs.audio.levels.musicUnderSpeechDb` — and the mix at −18.6 dB.

**The lesson is the sequencing, not the number.** The loop fix was verified by measuring
narration-silent windows, which correctly showed the bed present throughout. But **the
whole-file loudness was never re-checked after swapping the source**, and window
measurements cannot reveal an absolute level error — they show presence, not correctness.
Recorded as bug-ledger entry 16.

## ⚠️ A file bed cannot duck — one gain must serve two targets

`knobs.audio.levels` asks for **−36 dB under speech** and **−30 dB in gaps**; the 6 dB lift
is what makes tuned silence feel deliberate rather than empty.

The generated bed achieved that because `make-music.mjs` takes `vo-envelope.json` and bakes
sidechain ducking in. **`remux-music.mjs` has no sidechain path for a file bed**, so the
track plays flat and one gain must satisfy both. Chosen to satisfy the under-speech target,
because an intrusive bed is worse than a quiet gap:

| | Target | Measured at gain 0.055 |
|---|---|---|
| Under speech | −36 dB | **−36 dB** ✅ |
| In gaps | −30 dB | −36 dB (6 dB under) |

Consequence, visible in `check-levels`: the **lead-in reads −44.0 dB against the sibling's
−29.3** — the video opens in near-silence rather than with a bed establishing before the
narration. That is the track's own quiet intro plus the flat gain. **Not fixed** — the
music was settled and this needs either a sidechain in `remux-music.mjs` or a start offset.

### Authoring traps that only surface after a capture

These were **my** errors, not the engine's — but all three are invisible until frames
exist, which makes them expensive. All three are now pinned by tests.

1. **Trigger targets must be segment-qualified.** The builder emits `scenario-item-0`,
   `twotier-node-lane_ui`, `loop-edge-3`. A bare `item-0` resolves to `null`,
   the element is never revealed, and the segment renders as **a title over an empty
   stage** with no error. Cost a full draft capture+encode cycle.
2. **Edges need an explicit `drawEdge` (or `flowEdge`) trigger.** `revealNode` does not
   draw them. A diagram of disconnected boxes looks plausible in the storyboard.
3. **A diagram `viewBox` must match the band the builder gives it.** `.diagram-svg` is
   `width:100%` with `max-height:58vh` and `preserveAspectRatio="xMidYMid meet"`, so a
   16:9 viewBox letterboxes **to height** and renders at ~0.35 scale — legible in the
   storyboard, unreadable in the video. Re-laid out all six diagrams onto `0 0 1600 520`
   (~3:1), which roughly doubled effective label size.

> **The cheapest canary for all three: the capture dedup ratio.** The blank first draft
> deduped at **96%** (159 unique frames of 3,760). Once the content actually animated it
> dropped to **2%**. A suspiciously high dedup ratio means nothing is moving — check it
> before spending an encode.
